# ADR-002: sqlc for type-safe database access

**Status:** Accepted  
**Date:** 2026-04-29

## Context

SQL injection prevention is listed as an architectural requirement, not a code review concern. The question is how to enforce it structurally rather than through discipline.

Options considered:

1. **Raw `database/sql` or `pgx` with parameterized queries** — parameterized queries prevent injection, but nothing stops a developer from accidentally constructing a query string with `fmt.Sprintf`. Enforcement is entirely through discipline and review.

2. **An ORM (GORM, Ent)** — ORMs abstract SQL but introduce their own complexity, generate queries that are hard to inspect and optimize, and don't eliminate the risk of raw query escape hatches.

3. **sqlc** — SQL is written by hand in `.sql` files, reviewed as code, and sqlc generates type-safe Go functions from them. There is no mechanism in the generated code to construct queries dynamically. SQL injection becomes architecturally impossible at the application layer.

## Decision

sqlc.

Query files in `db/queries/` are the source of truth. The generated code in `internal/gen/dbgen/` is never edited by hand and is regenerated by `make generate`. The migration files in `db/migrations/` define the schema sqlc compiles against.

## Consequences

- Every database query is a readable SQL file that can be reviewed, explained, and optimized independently of Go code
- Adding or changing a query requires a deliberate step (write SQL, run generate, use generated function) — this friction is intentional
- The generated code is verbose but predictable — contributors know exactly what SQL runs for any repository call
- ORM convenience features (eager loading, associations) are absent — joins are written explicitly in SQL
- sqlc's PostgreSQL support is mature; edge cases in complex query types may require workarounds
